## Synthèse / verdict

L'état **technique** est sain : build, typecheck, lint et 272 tests passent. Aucun blocant de *compilation*.

Mais l'audit révèle **un blocant produit majeur à corriger AVANT de saisir du vrai contenu** : la règle « un sujet `confidentiel` n'est jamais visible au visiteur public » — documentée comme une décision durable — **n'est en réalité appliquée que dans l'assistant RAG, pas sur le site web**. Tant que la BDD ne contient que des sujets de test, le risque est nul ; dès que tu créeras un vrai sujet confidentiel, il fuitera publiquement. C'est le constat le plus important du rapport.

Second blocant fonctionnel : la fonctionnalité **sujets transversaux** (B5) est cassée — clic depuis l'autre labo → 404 systématique.

Le reste : robustesse (races, rate-limiting serverless, gestion d'erreur SSE) et une checklist d'env vars pour la mise en ligne.

## 🔴 Bloquant

### B1 — Les sujets `confidentiel` fuitent aux visiteurs publics (web UI + API REST)
*Dimension : Sécurité. Recoupe une décision produit documentée (mémoire, STATUS §Astra décision 2).*

Le filtre `confidentiel` est correctement appliqué dans l'assistant (SQL `match_rag_chunks` + outils `list_entities`/`find_tasks`), **mais absent de tout le parcours web principal** :

- **Grille Lab** — `src/app/[locale]/[lab]/page.tsx:25` : le RSC charge `subjects.select('*').or('labo.eq…,is_transversal.eq.true')` **sans filtrer `confidentiel`**. `SubjectGrid` ne masque que les boutons d'édition (`canEdit`), jamais les cartes. → visiteur non connecté voit les sujets confidentiels dans la grille, la recherche et les filtres.
- **Page Paper** — `src/app/[locale]/[lab]/paper/[id]/page.tsx:31-43` : charge n'importe quel sujet par id **sans gating**, et sérialise vers le client le contenu complet, les **tâches**, les **commentaires** et les **liens Dropbox**. Accès direct par URL. `generateMetadata` fuite aussi le `titre`.
- **`GET /api/subjects?lab=…`** — `src/app/api/subjects/route.ts:11-24` : aucune garde, aucun filtre `confidentiel`.
- **`GET /api/subjects/[id]`** — `src/app/api/subjects/[id]/route.ts:11-17` : aucune garde ; renvoie n'importe quel sujet confidentiel par id.

**Impact** : violation directe de l'exigence « `confidentiel` → jamais visible au visiteur ». Dès qu'un vrai sujet confidentiel existe, il est exposé via navigation, recherche, accès direct URL et fichiers liés.

**Correctif suggéré** : dériver le tier via `getSession()` puis, pour les non-membres, exclure `confidentiel=true` dans (a) le RSC de la grille, (b) le RSC de la page Paper (`notFound()` si confidentiel + non-membre), (c) `GET /api/subjects`, (d) `GET /api/subjects/[id]`. Idéalement une clause/vue partagée, comme le fait déjà le RAG. ⚠️ Voir interaction avec B2.

### B2 — Les sujets transversaux donnent un 404 systématique depuis l'autre labo
*Dimension : Qualité du code (BUG-001, confiance haute). Feature B5 (mémoire `b5-cross-lab-pas-isolation`).*

`src/app/[locale]/[lab]/paper/[id]/page.tsx:43` : la garde est `if (!subject || subject.labo !== lab) notFound()`. La grille remonte bien les sujets transversaux de l'autre labo (`.or(…is_transversal.eq.true)`) et `SubjectGrid.openPaper` navigue vers `/${locale}/${lab}/paper/${id}` avec le labo **de la page courante**. Donc pour un sujet transversal Paris ouvert depuis Montréal : `'paris' !== 'montreal'` → `notFound()`. Le champ `is_transversal` n'est jamais consulté dans la garde.

**Impact** : tout sujet transversal cliqué depuis l'autre labo hard-404. La visibilité transversale (livrée en PR #6) est non-fonctionnelle.

**Correctif suggéré** : `if (!subject || (subject.labo !== lab && !subject.is_transversal)) notFound()`, OU naviguer via `subject.labo` dans `SubjectGrid.openPaper`. **À combiner avec B1** : la garde finale doit autoriser le transversal **et** refuser le confidentiel aux non-membres.

### B3 — Env vars de déploiement (bloque la mise en ligne, pas le remplissage local)
*Dimension : Prêt-prod. Regroupe les points 🔴/🟠 de configuration.*

- **`NEXT_PUBLIC_APP_URL=http://localhost:3000`** (`.env.local:10`, fallback dans `robots.ts:4`, `sitemap.ts:7`, `[locale]/layout.tsx:12`, `lib/app-url.ts:5`). Si non posée sur Vercel → `robots.txt`, `sitemap.xml`, `metadataBase`/OpenGraph et **tous les liens d'emails (invitation, résultat de proposition)** pointent vers localhost → SEO cassé + invitations inutilisables.
- **`REPORT_EMAIL` non posé** (`lib/resend/send-report.ts:8-11`) → form « Signaler un problème » affiche « envoyé » mais aucun mail ne part (voir M8).
- **`SEED_ADMIN_EMAIL` absent** de `.env.local` (`scripts/seed-admin.ts:10`) → `npm run seed:admin` échoue immédiatement (`process.exit(1)`).
- **`EMAIL_FROM` / domaine Resend** : défaut `'FAME <noreply@fame-lab.eu>'`. Si `fame-lab.eu` n'est pas vérifié (SPF/DKIM) dans Resend, **tous** les envois sont rejetés — or l'invitation membre est le seul onboarding.

Voir la **Checklist go-live** en fin de rapport. (`.env.local` n'est **pas** suivi par git — vérifié, pas de fuite de secrets dans le repo.)

## 🟠 Important

### I1 — `GET /api/publications` ignore le filtre `lab` → mélange Paris/Montréal
`src/app/api/publications/route.ts:11-15` : valide `lab` (400 si invalide) mais la requête n'a **aucun** `.eq('labo', lab)` — renvoie les publications des deux labos. Les routes sœurs (`members:14`, `proposals:33`) filtrent, donc c'est une omission (≠ décision cross-lab, qui ne concerne que les sujets). Impact : page Publications de Paris affiche aussi celles de Montréal ; stats sidebar, regroupements par année et compteurs faussés. **Correctif** : ajouter `.eq('labo', lab as Lab)`.

### I2 — Les tâches des sujets transversaux disparaissent après la 1re mutation kanban
SSR `src/app/[locale]/[lab]/tasks/page.tsx:34-38` charge via une cascade `.in('sujet_id', visibleSubjectIds)` (incluant les transversaux de l'autre labo), mais `KanbanBoard.refresh()` rappelle `GET /api/tasks?lab=…` qui filtre `.eq('labo', validLab)` (`api/tasks/route.ts:23`). Après tout claim / changement de statut / sous-tâche / ajout / suppression, le re-render repart du jeu filtré → les tâches cross-lab disparaissent jusqu'au reload complet. **Correctif** : faire refetcher `refresh()` via la même cascade (endpoint acceptant `subject_ids`), ou fusionner au lieu de remplacer.

### I3 — Rate-limiting en mémoire inefficace en serverless + IP falsifiable
*Recoupé par deux agents (qualité BUG-003, sécurité #4).*
`src/lib/rate-limit.ts:3-16` stocke les hits dans un `Map` au niveau module. Sur Vercel (multi-instances/cold-starts), chaque instance a son propre compteur → limite contournable par scaling. `clientIp()` prend le premier `x-forwarded-for`, falsifiable → reset du compteur par rotation d'en-tête. Touche **`sign-in`, `comments`, `proposals`** (et `report`). L'assistant utilise déjà `checkRateLimitDb` (persistant) — bon modèle à répliquer. **Impact** : spam de commentaires/propositions, brute-force sign-in facilités en prod. **Correctif** : porter ces routes sur un rate-limit DB-backed ; ne se fier qu'à l'IP fournie par la plateforme.

### I4 — `POST /api/report` sans auth ni rate-limit → bombardement d'emails
*Recoupé (parcours #8, sécurité #3).*
`src/app/api/report/route.ts:6-18` : n'importe qui peut POST en boucle (jusqu'à 5000 car.) → emails Resend vers `REPORT_EMAIL`, contrairement à sign-in/comments/proposals. **Impact** : abus/DoS email, coût Resend, spam admin. **Correctif** : appliquer `rateLimit('report:'+clientIp(req), …)` (helper existant), idéalement DB-backed (cf. I3).

### I5 — Race condition `proposal → convert` crée des sujets orphelins
`src/app/api/proposals/[id]/convert/route.ts:16-65` : la garde d'idempotence (`if (proposal.subject_id)`, ligne 24) lit avant l'insert. Deux requêtes admin concurrentes (double-clic) lisent toutes deux `subject_id: null`, insèrent toutes deux dans `subjects`, puis la 2e update écrase la 1re. Le 1er sujet créé n'a plus aucune proposition pointant vers lui → orphelin permanent (la compensation lignes 57-62 ne couvre pas ce cas). **Probabilité faible, conséquence durable.** **Correctif** : garde de transition d'état (`if proposal.statut === 'accepted' → 409`) avant l'insert, OU contrainte unique DB sur `proposals.subject_id`, OU RPC Postgres atomique.

### I6 — Chat SSE : coupure réseau en cours de stream → chat gelé en `streaming`
`src/lib/assistant/useAssistantChat.ts:60-73` : le `for(;;){ await reader.read() … }` n'a pas de try/catch. Le fetch initial et les codes HTTP sont gérés, mais une coupure en cours de stream (réseau, `reader.read()` qui throw) sort de `send` en rejet non géré : le placeholder vide reste, `status` reste `'streaming'`, le composer reste désactivé, l'indicateur tourne indéfiniment. Une simple coupure réseau gèle le chat jusqu'au reload. **Correctif** : entourer la boucle d'un try/catch (→ `setStatus('error')` + retirer le placeholder) + un `finally` normalisant le statut. (Voisin de M1.)

## Points vérifiés — CONFORMES (rien à faire)

Rassurant : une large part du site est solide.

- **Secrets server-only** : aucun `process.env` non-`NEXT_PUBLIC_` dans un fichier `'use client'`, aucun module serveur (`supabase/server`, `dropbox`, `resend`, `llm`, `rag/*`) importé côté client (grep exhaustif). Conforme.
- **Piège service-role/RLS** : `createServiceClient()` (`src/lib/supabase/server.ts:33-42`) est bien **sans cookies**. Conforme à la mémoire `service-role-no-cookies`.
- **Next.js 16** : `params`/`searchParams` awaités partout (pages, layouts, `generateMetadata`, routes `[id]`). Aucun accès non-awaité.
- **Requêtes paramétrées** : pas d'interpolation SQL dangereuse. Les `.or('labo.eq.${lab}…')` interpolent un `lab` **validé contre `VALID_LABS`** → sûr.
- **AuthZ** : pages `admin/*` via `requireAdmin()`, `data`/`prompts` member-only, `members` PATCH protégé contre l'escalade de privilèges (field-gating self/admin). Tableau complet ci-dessous.
- **Assistant** : tier dérivé serveur, historique client sanitisé, anti-injection sur chaque tour user, modération OpenAI, kill-switch + budget, rate-limit DB persistant, IP hachée+salée, `get_subject_files` réservé aux membres.
- **i18n** : parité de clés EN↔FR stricte (0 manquante), zéro chaîne UI en dur significative (hors M14), aucune valeur anglaise résiduelle dans `fr.json`, tous les enums/domaines traduits, KB en parité complète. Aucun TODO/FIXME/lorem.
- **Build/typecheck/lint/test** : 🟢 `tsc` EXIT 0, `lint` EXIT 0, `vitest` 272/272, `next build` OK (~50 routes).
- **Migrations** : `001`→`009` présentes, cohérentes, appliquées en BDD. Embedding `text-embedding-3-large` réduit à `dimensions:1536` pour matcher `vector(1536)` — cohérent (⚠️ ne pas changer `ASSISTANT_EMBED_MODEL` pour un modèle sans réduction sans recréer la colonne).
- **SEO/infra** : `robots.ts`/`sitemap.ts`/`generateMetadata` corrects, en-têtes de sécurité de base présents (`next.config.ts`).
- **Décisions produit assumées** (non signalées) : emails membres publics, cross-lab non isolé (mémoire `b5-cross-lab-pas-isolation`).
